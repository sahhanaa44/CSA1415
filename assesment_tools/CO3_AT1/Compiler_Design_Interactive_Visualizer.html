Syntax-Directed Definition — Synthesized Attributes

Parses an arithmetic expression into a syntax tree, then evaluates it bottom-up: each internal node computes its value only after both children are known, and that value is synthesized upward toward the root.

q1 / sdd.expr

Concept

Every node's value is synthesized from its children — evaluation flows strictly bottom-up. Precedence (* / / before + / -) and associativity are baked into the tree shape itself.

Step 0 of 0

How it works

The expression is tokenized and parsed with a recursive-descent parser (E → E±T | T, T → T×F | T÷F | F, F → num | (E)) so the tree structure alone encodes precedence. Click Next / Auto Run to watch each node combine its children's synthesized values.

Question 02
Postfix Expression Evaluation — Stack Machine

Reads a postfix (Reverse Polish) expression token by token. Operands are pushed; operators pop two operands, compute a result, and push it back — a direct, mechanical model of bottom-up, S-attributed evaluation.

q2 / postfix.expr

Concept

Postfix removes the need for parentheses or precedence rules at evaluation time — a stack alone is enough, which is exactly why compilers translate expressions into postfix / three-address form.

Step 0 of 0

How it works

Tokens are read left to right. Numbers are pushed. An operator pops the top two values (b then a), applies a op b, and pushes the result. This is the classic S-attributed / bottom-up evaluation strategy.

Question 03
L-Attributed Definition — Inherited + Synthesized

Demonstrates the two directions of attribute flow in one tree: an inherited environment is passed top-down from parent to children (left to right), while each node's value is synthesized bottom-up once its children are known — the defining trait of an L-attributed definition.

q3 / lattr.expr

Concept

The variable environment is inherited: it only ever depends on the parent (or a left sibling), so it can be passed downward during a single left-to-right, top-down traversal. Each identifier's value is then synthesized back upward.

Step 0 of 0

How it works

Phase 1 (blue arrows): the environment {a,b,c} is copied down from the root to every leaf — an inherited attribute. Phase 2 (amber → green): identical to Q1, values combine bottom-up as synthesized attributes, respecting precedence from the tree shape.

Question 04
Type Equivalence Checker — Structural Comparison

Breaks two type expressions down into pointer layers plus a base type, then compares them layer by layer — the same structural-equivalence check a compiler's semantic analyzer performs before allowing an assignment or operation.

q4 / types.cmp

Concept

Two types are structurally equivalent when they have the same pointer depth and the same base type. int* and char* are not equivalent even though both are pointers, because their base types differ.

Try: int, float, char, double, int*, char*, int**

Step 0 of 0

How it works

Each type string is stripped of trailing * characters to count pointer depth, leaving a base type. The checker compares pointer depth first, then the base type — mirroring how a symbol table stores and compares type descriptors.

Question 05
Semantic Type Checking — Arithmetic Expressions

Simulates a semantic analyzer validating an arithmetic operation between two operand types, applying the usual arithmetic-conversion rules (char → int → float) to decide the result type — or to flag an error.

q5 / typecheck.expr

Concept

When operand types differ, the compiler inserts an implicit conversion — promoting the "narrower" type to the "wider" one — before applying the operator. This is why int + char is valid: char is promoted to int.

Step 0 of 0

How it works

Each type is ranked (char < int < float). If the ranks differ, the lower-ranked operand is promoted to match the higher one before the operator is applied. Division by a zero-valued type is not evaluated here — this checks type compatibility, not runtime values.
